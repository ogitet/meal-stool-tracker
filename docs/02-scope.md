> 画面の構成や遷移は Structure、配置や見た目は Skeleton 以降で扱う。
>
> - 状態：確定（2026-11-09）、間食の統合を反映（2026-11-10）
> - 記法：末尾の `→Q番号` は 7章の判断事項に対応する。

---

## 1. スコープの考え方

- 判断基準は Strategy の目標 G1（継続）を最優先とする。
- 記録の種類は食事と便の2つとする。間食は食事の「その他の食事」として記録する（Q29）。
- 記録時の必須入力は、食事はカテゴリ、便は形状のみとする。
- 将来の拡張（傾向分析、ブリストルスケール）のために今作る機能は増やさない。データの持ち方で備える。

## 3. 機能要件

### F-01 食事記録

| # | 要件 |
|---|---|
| 1 | 食事枠として朝食・昼食・夕食を選んで記録できる |
| 2 | 固定枠とは別に、必要に応じて「その他の食事」を追加できる。間食もここに記録する |
| 3 | 定義済みのカテゴリから複数選択して記録できる。食べたものだけを選べばよい |
| 4 | 食事量、カロリー、重量は入力しない |
| 5 | 今日の分は日付の入力なしで記録できる。過去の日付の分も記録できる（記録し忘れへの対応） |
| 6 | カテゴリを1つ以上選ばないと保存できない →Q10 |
| 7 | 朝食・昼食・夕食は1日につき各1件とする。すでに記録がある枠は、新規ではなく既存の記録の編集になる →Q11 |
| 8 | その他の食事は食べたタイミングごとに1件ずつ、1日に何件でも記録できる。名称は固定とし、自由記述の名前は付けない →Q11 |
| 9 | 食事に時刻の入力は求めない。日付と食事枠で扱い、作成日時のみ自動で保持する →Q6 |
| 10 | どの食事枠でも、お菓子グループを含むすべてのカテゴリを選択できる →Q29 |

### F-03 便記録

| # | 要件 |
|---|---|
| 1 | 排便ごとに記録でき、1日に複数回記録できる |
| 2 | 形状（硬い／普通／柔らかい／下痢）を1つ選んで記録する |
| 3 | 量（少／普通／多）は任意で記録できる |
| 4 | 排便感（すっきり／残便感あり）は任意で記録できる |
| 5 | 記録時刻は自動取得する |
| 6 | 過去の日付の分も記録できる（記録し忘れへの対応） |
| 7 | 過去の日付に追加した場合、日付はその日、時刻は記録操作時の時分を初期値とする →Q5 |

### F-04 週カレンダー

| # | 要件 |
|---|---|
| 1 | 週単位の表示をアプリの中心とする |
| 2 | 前後の週に移動できる |
| 3 | 日ごとに、食事と便の記録をアイコンで表示する |
| 4 | 今日の日付を視覚的に強調する |
| 5 | 日付を選択すると、その日の詳細を確認できる |
| 6 | 便の形状4種を見分けられる |
| 7 | カテゴリが多い日でも視認性を維持する |
| 8 | 日別詳細を開かなくても、揚げ物など個々のカテゴリを判別できる（G2 の判断基準「今週は揚げ物が多い」と言える状態を満たすため） →Q12 |
| 9 | 週の開始曜日は月曜とする →Q13 |

### F-05 日別詳細

| # | 要件 |
|---|---|
| 1 | 選択した日の朝食・昼食・夕食とその他の食事（間食を含む）を確認できる |
| 2 | 選択した日の排便記録を確認できる |
| 3 | 各記録の編集・削除に進める |
| 4 | 選択した日に記録を追加できる（F-01、F-03 の過去日の記録に対応） |

### F-06 記録の編集・削除

| # | 要件 |
|---|---|
| 1 | 食事・便のすべての記録を編集できる |
| 2 | 食事・便のすべての記録を削除できる |
| 3 | バックアップがないため、削除は誤操作を防ぐ確認を経て実行する |
| 4 | 便の日時は、編集で修正できる →Q5 |

### F-07 本人のみのアクセス

Strategy のリスク対応（クラウド上の機微な情報の保護）から必要となる機能。

| # | 要件 |
|---|---|
| 1 | 本人以外はデータを閲覧・変更できない |
| 2 | 利用者は本人1名のみとし、一般向けの新規登録は設けない |
| 3 | 一度ログインすれば、通常の利用では毎回のログインを求めない（G1 のため） |

### F-08 スマホ向けPWA

| # | 要件 |
|---|---|
| 1 | スマホの画面サイズに最適化する。PC向けの最適化は行わない |
| 2 | スマホのホーム画面に追加して起動できる |
| 3 | オンラインでの利用を前提とし、オフライン時の記録はMVPでは対応しない →Q14 |

### F-09 前回の食事のコピー

| # | 要件 |
|---|---|
| 1 | 朝食・昼食・夕食それぞれについて、前回の同じ枠の記録をコピーできる |
| 2 | コピー後、保存する前に内容を変更できる |
| 3 | テンプレート管理機能は作らない |
| 4 | 「前回」は、記録しようとしている日より前で最も新しい同じ枠の記録とする |
| 5 | 現在は使っていないカテゴリ（F-11）はコピーの対象にしない |
| 6 | その他の食事（間食を含む）はコピーの対象外とする →Q8 |

### F-10 月カレンダー

| # | 要件 |
|---|---|
| 1 | 週表示と切り替えて、月単位で表示できる |
| 2 | 前後の月に移動できる |
| 3 | 日ごとに便の記録をアイコンで表示する。食事のアイコンは省略してよい |
| 4 | 今日の日付を視覚的に強調する |
| 5 | 日付を選択すると、その日の詳細を確認できる |

### F-11 カテゴリ管理

対象は食事カテゴリ（お菓子グループを含む）とする。便の選択肢は管理の対象外とする。

| # | 要件 |
|---|---|
| 1 | カテゴリを追加できる |
| 2 | カテゴリの名称を変更でき、過去の記録にも新しい名称が表示される →Q7 |
| 3 | カテゴリは削除せず「使わない」状態にする。選択肢には出なくなるが、過去の記録には残る →Q7 |
| 4 | カテゴリの所属グループ（主食、肉・魚・卵、お菓子など）を変更できる →Q15 |
| 5 | グループ自体の追加・変更、カテゴリの並び替えは MVP では行わない →Q15 |

## 4. 品質要件

| 観点 | 要件 |
|---|---|
| 入力の速さ | 便は約5秒、食事は約15秒で記録が完了する（Strategy の目安） |
| 表現 | 食事と便の関係について、因果関係の断定や医学的な判断・助言をしない |
| 運用コスト | クラウドサービスの無料枠の範囲で運用できる |
| 日付の区切り | 端末の暦日（0時）で区切る。深夜の食事を前日分にしたい場合は、日付を選んで記録する →Q16 |

## 5. コンテンツ要件

### 記録するデータ

データベース設計ではなく、保持すべき情報の定義。

| 記録の種類 | 保持する情報 | 必須 |
|---|---|---|
| 食事 | 日付 | 必須 |
| | 食事枠（朝食／昼食／夕食／その他の食事） | 必須 |
| | カテゴリ（複数） | 必須 →Q10 |
| | 作成日時 | 必須（自動取得） →Q6 |
| 便 | 日時 | 必須（自動取得） |
| | 形状 | 必須 |
| | 量 | 任意 |
| | 排便感 | 任意 |

### 初期カテゴリ

**食事カテゴリ（26種）** →Q38

| グループ | カテゴリ |
|---|---|
| 主食 | 米、パン、麺 |
| 肉・魚・卵 | 豚肉、鶏肉、牛肉、魚、卵、大豆製品 |
| 野菜・果物 | 野菜、海藻、きのこ、果物 |
| その他 | 揚げ物、乳製品、辛いもの、お酒、コーヒー |
| お菓子 | ポテチ、グミ、チョコ、せんべい、アイス、菓子パン、クッキー、その他 |

**便の選択肢**

| 項目 | 選択肢 |
|---|---|
| 形状 | 硬い、普通、柔らかい、下痢 |
| 量 | 少、普通、多 |
| 排便感 | すっきり、残便感あり |

### 表示用のコンテンツ

| コンテンツ | 要件 |
|---|---|
| 便の形状のアイコン | 4種を区別できるものを用意する |
| 食事カテゴリの表示 | カレンダーで識別できる表現を用意する。具体的な表現は Skeleton / Surface で決める |
| 追加したカテゴリの表示 | 追加時に画像の用意や選択を必須にしない →Q12 |

### 将来の拡張への備え

| 将来の機能 | 今の時点で満たすこと |
|---|---|
| 月ごとの集計（G3 の判断基準：揚げ物を食べた日の数） | カテゴリと日付の組み合わせで日数を数えられる |
| 食事と便の傾向分析 | 各記録の日付または日時が残っている。「その日の便」の定義は分析機能を作るときに決める（→Q9） |
| ブリストルスケール7段階 | 形状の選択肢を増やしても、既存の4段階の記録が失われない |
| カテゴリ分類の見直し | カテゴリの名称や所属グループを変えても、過去の記録との対応が保たれる |

## 7. 判断事項

すべて 2026-11-09 に確定済み。

### Strategy からの持ち越し

| # | 問い | 決定 | 理由 |
|---|---|---|---|
| Q5 | 記録時刻を後から修正できるか | できる。便の日時を編集で修正する。記録時には時刻の入力を求めない | 自動取得の手軽さを保ちつつ、記録し忘れに対応できる |
| Q6 | 食事にも時刻を持たせるか | 時刻の入力は求めない。すべての食事で作成日時を自動で保持し、画面には表示せず修正もしない（2026-11-10 改定） | 間食の統合により「間食のみ自動取得」は成立しなくなった。操作を増やさずに、将来の分析に使える情報を残す。ただし過去の日に追加した場合は、実際に食べた時刻を表さない |
| Q7 | カテゴリを変更・削除したとき、過去の記録をどう扱うか | 名称変更は過去にも反映する。削除の代わりに「使わない」状態にして過去の記録を残す | 過去の記録が失われない。ただし、意味が変わる改名は集計を歪めるため、その場合は新規カテゴリを追加する運用とする |
| Q8 | 追加の食事にコピー機能を適用するか | 適用しない | 要件は朝・昼・夕のみで、追加の食事には「同じ枠」の意味が定まらない |
| Q9 | 「その日の便」をどう定義するか | MVP では定義しない。日付と日時を残し、分析機能を作るときに決める | 今決めなくても、データが残っていれば後から判断できる |

### Scope で新たに出たもの

| # | 問い | 決定 | 理由 |
|---|---|---|---|
| Q10 | 食事でカテゴリを1つも選ばない保存を許すか | 許さない | 空の記録は振り返りに使えない。何か食べたことだけ残したい場合が多ければ見直す |
| Q11 | 同じ日に同じ枠の記録を複数作れるか | 朝・昼・夕は各1件。2回目は「その他の食事」で記録する | カレンダーと「前回のコピー」の意味が明確になる |
| Q12 | 週カレンダーにどの粒度で食事を表示するか | カテゴリ単位で判別できるようにする。追加カテゴリのために画像の用意は求めない | グループ単位だと「揚げ物」が同じグループの他の項目に埋もれ、G2 の基準を満たせない。全26種の表示をスマホ幅に収める方法が Skeleton の主要課題になる |
| Q13 | 週の開始曜日 | 月曜 | 週末を含めて1週間を振り返りやすい |
| Q14 | オフラインでの記録に対応するか | MVP では対応しない | 再接続時の同期が実装を大きく複雑にする。使っていて困る場面が多ければ追加する |
| Q15 | カテゴリ管理をどこまで作るか | 追加、名称変更、「使わない」設定、所属グループの変更まで。グループ自体の編集と並び替えは作らない | 「基本的なカテゴリ管理」の範囲に留める |
| Q16 | 1日の区切りをいつにするか | 暦日（0時） | 最も単純。深夜の食事は日付を選べば前日分にできる |
| Q29 | 間食をどう記録するか（2026-11-10 変更） | 独立した記録の種類にせず、「その他の食事」として記録する。間食カテゴリは食事カテゴリの「お菓子」グループとする | 記録の入口を食事と便の2つに絞る。元の要件「間食は通常の食事と分けて記録する」を置き換える |
| Q38 | 食事カテゴリの分類（2026-11-10 見直し） | 5グループ26種（5章）。調理方法グループを廃止して揚げ物のみ「その他」に残す。汁物、主食とたんぱく質の「その他」を削除。辛いもの、お酒、コーヒーを追加 | 知りたいのは揚げ物かどうかだけで、他の調理方法は不要。便との関係で見たいものを「その他」に集め、振り返りに使わない選択肢は減らす |
