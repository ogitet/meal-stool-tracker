---

## 1. プロダクトの一文定義

**食事と排便を数タップで記録し続け、カレンダーで振り返ることで、自分の体の傾向に気づくための個人用記録基盤。**

カロリーや栄養素を正確に管理するツールではない。「何系のものを食べ、便がどうだったか」を大まかに、途切れず残すことに価値を置く。

---

## 2. ユーザーニーズ

### 対象ユーザー

自分自身のみ（開発者＝利用者）。他者への提供は現段階では考慮しない。

### 利用の文脈

| 場面 | 状況 | 求めていること |
|---|---|---|
| 食後 | 手短に済ませたい。細かく思い出したくない | 考えずに数タップで終わる |
| 排便後 | その場ですぐ記録したい | 形状を選ぶだけで終わる |
| 記録し忘れたとき | 後から思い出して入れる | 取りこぼしを気軽に埋められる |
| 振り返るとき | 週末や体調が気になったとき | 最近の食事と便を一目で見渡せる |

### 満たすべきニーズ

1. **続けられること**：面倒にならず、忙しい日でも記録が途切れない
2. **食事傾向が見えること**：米・麺・揚げ物・お菓子などへの偏りに気づける
3. **排便傾向が見えること**：便の状態や回数の推移がわかる
4. **食事と便を並べて見られること**：同じ時間軸上で眺め、自分なりの気づきを得られる
5. **あとから使えるデータが残ること**：将来の傾向分析に耐える形で蓄積される

### 既存の手段では満たされない点

一般的な食事管理の手段は、カロリーや食品の正確な入力を求める傾向があり、その負担が継続の妨げになる。本プロダクトは精度を意図的に手放し、記録の負担を下げることで差をつくる。

---

## 3. プロダクト目標

| # | 目標 | 位置づけ |
|---|---|---|
| G1 | 記録を習慣として継続できる状態をつくる | **最優先** |
| G2 | カレンダーを見るだけで、直近の食事と便の傾向がつかめる | MVPで達成 |
| G3 | 将来の傾向分析を妨げないデータを蓄積する | MVPでは土台のみ |

G1 と他の目標が衝突した場合は、G1 を優先する。

### 成功の判断基準

個人利用のため、厳密なKPIは置かず、次の問いに実感で答えられるかで判断する。数値は目安であり、実際の利用を踏まえて見直す。

| 目標 | 判断の問い | 目安 |
|---|---|---|
| G1 | 1か月使ったあとも、自然に記録を続けているか | 30日間のうち、8割以上の日に記録がある |
| G1 | 1件の記録が面倒に感じないか | 便は約5秒、食事は約15秒で完了する |
| G2 | カレンダーを開いて、今週の傾向を言葉にできるか | 日別詳細を開かずに「今週は揚げ物が多い」などと言える |
| G3 | 揚げ物を食べた日の数を月ごとに集計できるか | データ構造上、後から集計が可能である |

## 4. 設計原則

判断に迷ったときの基準。上にあるものほど優先する。

1. **入力の摩擦を最小化する**：数タップで完了する。自由記述・写真認識・食品検索を基本操作にしない
2. **正確さより継続性を優先する**：カロリー・重量・食事量は記録しない
3. **選択式を基本にする**：定義済みカテゴリから、食べたものだけを複数選択する
4. **記録と振り返りを分離する**：記録は素早く、確認はカレンダーと日別詳細で行う
5. **対象領域を絞る**：食事と便に特化する

加えて、次の2点を全体の姿勢とする。

- **因果関係を断定しない**：食事と便の関係は傾向として扱い、医学的な判断や助言はしない
- **過剰につくらない**：個人利用に見合う複雑さに留め、実際に使いながら改善する

## 5. 戦略上のスコープ境界

詳細な機能要件は Scope レイヤーで定義する。ここでは方向性のみを示す。

| MVPで扱う | 将来の検討対象 | 扱わない（初期バージョン） |
|---|---|---|
| 食事（間食を含む）・便の記録 | 食事と便の傾向分析 | AI・写真による食事記録 |
| 記録の編集・削除 | ブリストル便形状スケール（7段階）への拡張 | カロリー・栄養素の計算 |
| 前回の食事のコピー | | 食品データベース |
| カレンダー（週・月） | | SNS・ユーザー共有 |
| 日別詳細 | | 複雑な分析 |
| 基本的なカテゴリ管理 | | 通知 |
| | | 体重・運動・睡眠などの記録 |

提供形態は、スマホで使う個人利用のWebアプリ（PWA）とする。データは無料で使えるクラウドサービスに保存する。バックアップ・エクスポート機能は設けない。

## 6. 主なリスク

| リスク | 影響 | 方針 |
|---|---|---|
| 記録が面倒になり、やめてしまう | 目的全体が崩れる | G1 を最優先し、入力項目を増やす変更には慎重になる |
| カテゴリが多く、選択やカレンダーの表示が煩雑になる | 入力の負担増、俯瞰性の低下 | 頻出カテゴリの見せ方と集約表示を Skeleton レイヤーまでに検討する |
| 記録の抜けと「食べていない／排便がない」の区別がつかない | 振り返りや将来の分析の信頼性が落ちる | 入力の負担を避けるため区別しない。集計値は「記録された範囲の傾向」として読む |
| 傾向を因果関係と受け取ってしまう | 誤った自己判断につながる | 断定を避けた表現にする |
| 排便などの機微な情報が外部に漏れる | プライバシーの侵害 | クラウドに保存するため、本人以外がデータにアクセスできない構成にする |
| 無料枠の条件変更やサービス終了 | 記録を使えなくなる、または失う | バックアップを持たないことは受容する。サービス選定時に無料枠の条件を確認する |

## 7. 判断事項

### 決定済み

| # | 問い | 決定 |
|---|---|---|
| Q1 | データをどこに保存するか | 無料で使えるクラウドサービス（具体的なサービスは技術選定時に決める） |
| Q2 | 利用する端末はどれか | スマホのみ |
| Q3 | データのバックアップやエクスポートは必要か | 不要 |
| Q4 | 記録の抜けと「該当なし」を区別するか | 区別しない |

Q5 以降は [02-scope.md](02-scope.md) の7章で確定した。
